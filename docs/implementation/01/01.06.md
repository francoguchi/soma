# Reference data and Settings surfaces

## Outcome

Operators can manage Customers, Contacts, Dispatch Locations, descriptive Local User Profile metadata and typed settings through dense Settings/reference-data surfaces that preserve Foundation interaction semantics and explicit ambiguity/history.

## Work

### Backend

Only fixes required by live/browser exercise of already-owned scope-01 APIs. No new domain authority belongs here.

### Frontend

Implement Customer, Contact and Dispatch reference-data surfaces under `Settings → Reference data`; candidate and Account Code conflict review; channel/affiliation history and ambiguity; lifecycle blocker preview/archive/reactivate; Local User Profile display-name editing; and registered Settings presentation. Contextual deep links may enter these surfaces without creating a top-level Customers workspace.

Refine Reference into collection-only Browse, focused Create without pre-identity evidence, and the existing three-pane Open workbench. Preserve collection/filter/selection/page/scroll state across entry/return; separate entity navigation from New <type>/Refresh collection actions and make exact matching secondary. Keep Profile/Preferences compact and unboxed using shared form composition.

Reuse Foundation shell, collections, selection, working copies, confirmation/dialog behavior, error states and appearance semantics. Operator text says **Customer** while domain/API identity remains `CustomerOrganization`.

### Final usability and polish acceptance

R01.06-E is reopened for the one-collection interaction correction. For each reference type there is one primary collection and one selection model across Browse and Open. The ordinary active-list query, default exact search and expert matching are distinct query modes of that same visual list; no candidate grid is rendered alongside the ordinary grid. One server-owned count/ambiguity summary accompanies the active query. A unique candidate is still read-only evidence; explicit Open never accepts a relationship. Account Code review can show claimants in the primary collection without creating a second grid inside Details. The accepted Browse / Create / Open state model and all owner semantics remain unchanged.

The final surface optimizes discoverability before decorative terminal resemblance:

- **Browse** is the collection/search surface.
- **Create** is the focused creation workflow.
- **Open** is the three-pane inspection/workbench.
- navigation, search, collection state, commands, explanatory evidence and destructive actions have visibly different roles.
- ordinary operators do not need persistence, revision, byte-encoding, semantic-owner or internal query knowledge to understand common actions.

#### Search consistency

Where an owner exposes search/filter capability, render the shared Foundation search affordance in one predictable collection-associated location.

Search availability is owned by the authoritative search source, not by the current bounded page alone:

- searchable source available -> enabled;
- authoritative searchable source known empty -> visible but disabled with a concise accessible reason;
- source/capability unavailable -> visible but disabled/unavailable with a concise reason;
- current page empty while broader bounded owner search remains valid -> stays enabled.

Never implement a current-page-only client filter and present it as complete owner search. Default search uses one entry field only where supported by existing owner contracts. Expert exact fields, affiliation scope and historical lookup remain collapsed under Advanced search and change the same primary collection.

#### Operator copy and empty state

Pristine empty state is concise domain language such as `No Contacts yet.`, not simultaneous paging-engine output such as `No records in this page` plus `0 matching records`.

Counts appear when they add information: populated collections, active query/filter results, ambiguity, pagination or explicit evidence review. Singular/plural grammar is correct.

Precise UTF-8 byte/storage limits are secondary validation evidence unless byte precision is materially useful to the operator. Ordinary help text explains the human constraint first.

Profile/Preferences do not repeat an accepted value immediately beside the same editable value unless the repetition communicates distinct state.

#### Navigation, commands and rows

Whole-surface navigation such as `Back to list` belongs outside an individual Details pane because it changes the complete Reference surface.

Do not expose both Back and Cancel when they perform the same transition. If cancellation has distinct unsaved-work semantics, label and test that distinction explicitly.

Record names remain visually clean. Selected/opened/current/historical/focus evidence is separate from the record label. Selection, opened identity and keyboard focus remain distinct states.

Open-mode empty owner collections use owner language such as `No channels yet.` rather than generic zero-page output when pagination evidence adds no value.
